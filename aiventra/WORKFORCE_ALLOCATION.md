# Workforce allocation

## Task-specific increment

Each versioned task can now carry a workstream, skills, complexity/risk, required authorized tools, context allowance, acceptance/QA criteria and recommended/exact model IDs. Server-generated decisions and reasons are saved in immutable-by-API revisions; current eligibility is separately recomputed for display. Approval creates actual logical assignments, dependencies, task budgets and profile-bound payloads. Existing bounded scheduler capacity, pause/recovery and separate coding approvals remain authoritative.

Automatic/manual/hybrid modes and individual draft overrides are connected to the Planning UI and worker. Unknown/foreign/paid/incapable/policy-excluded models and unauthorized tools are rejected. Missing free/manual assignments wait without a model run or reservation. Complexity/risk, context, registry quality/reliability, current task-case benchmarks, project sensitivity and scoped policies inform choices. Context allowances are constraints, not measured RAM estimates. Historical records lacking new metadata keep their existing behavior. Manual changes after started work need newly approved follow-up scope; automatic failure fallback remains bounded and persisted.

## Current allocation status

Versioned approved workforce plans, dependencies, concurrency caps, persistent scheduling, reassignment and pause/recovery exist; WORKFORCE_PLANNING.md records their actual scope. Live allocation execution now also obeys ZERO_COST_ONLY. Lack of an eligible free model saves a waiting task and assigned logical agent without fake progress or automatic remote fallback. Earlier missing-feature statements below are historical.


The application currently has configurable registered roles, explicit owner-assigned specialist document work, approved fixed planning tasks, employee tool/routing caps and persisted invocation state. General meetings can create at most four selected-participant document follow-ups within their original job cap. These operations are not requirements-based autonomous staffing.

Milestone C must generate and version team/task proposals from requirements, role skills and budget/capacity; exact owner approval must precede allocation. Add distributed capacity/concurrency controls, dependencies, budget-aware scheduling and visible assignment/capacity evidence. A registered/enabled employee must never be counted as active live inference without a real call and valid worker lease.
