New-project preferences support automatic/manual/hybrid allocation, eligible worker pools and exact role/department assignments. Workforce drafts additionally support per-task overrides, strict workstream/skill/tool/risk/context/QA contracts and saved model explanations. Preferences cannot approve repositories, PRs or release. See LEAD_AI_ORCHESTRATION.md and WORKFORCE_ALLOCATION.md for current scope and evidence limits.

The policy-rules-v1 planner reads the approved requirement and reuses the project's four existing foundation tasks. It proposes requirements, cost, design, frontend/backend, database and integration work as applicable, plus security assessment and independent coding review/QA capacity. This is deterministic policy evaluation, explicitly labeled; it does not claim an AI planning call. Owners can change objectives, assignees, dependencies, task caps, logical slots, mode and concurrency before exact version/hash approval.

Plans, immutable-by-API revisions, task edges, assignments and approval records are stored in SQL. At most 32 tasks and 16 logical slots are allowed; each role has one or two slots. No per-role model process is started. Registry capabilities, scoped policies, price freshness and model availability inform estimates. Unknown rates/eligible models yield unknown estimates. Token allowances are estimates, not invoices; the existing gateway rechecks actual prompt size and every overlapping cap before reserving funds.

Approval creates tasks once, a shared staffing budget, individual task budgets and durable assignment messages. Foundation work is preserved. Documents run only after their dependency artifacts exist. Coding tasks wait for an imported repository, fixed suite and a separate repository-change approval. Staffing approval cannot authorize code execution or deployment. Plans cannot be edited after approval; new scope requires new approval rather than silent expansion.

Distributed workflow admission locks the organization, counts active SQL leases and enforces global, plan and agent capacity. The worker uses a bounded pool, renews active leases, and keeps heartbeat/watchdog/indexing separate from workflow calls. Expired work resumes from checkpoints; successful calls are reused, and uncertain/started calls require owner reconciliation. Existing messages, structured meetings and bounded delegation share the same worker/gateway. Parallel tasks are real independent DAG nodes, not generated progress percentages.

Pause revokes leases and records the previous task/workflow state without modifying approved coding payloads. Resume retains checkpoints, renews the owner-authorized time window and refuses unreconciled model/runner work. Reassignment is restricted to unexecuted document work, approved allocations and the same department; it records owner/reason/history and a task revision. Paid, completed and coding assignments cannot be silently transferred.

The connected allocation dashboard shows actual task states/checkpoints/errors, claims, caps, spending and registry evidence. Its test adapter is explicitly labeled deterministic, with no live AI claim. The separate engineering workspace shows execution logs, diffs and approval evidence. API access remains tenant-scoped and owner-only.
