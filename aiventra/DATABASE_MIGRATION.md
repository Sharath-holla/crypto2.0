# SQLite to PostgreSQL transfer and explicit cutover

**Deferred by owner choice:** the application will continue using SQLite. This guide, PostgreSQL schema/pgvector definitions and transfer tooling are retained for a future explicitly requested migration. Do not perform the cutover steps or request PostgreSQL credentials as part of normal continuation.

Milestone 2 implements an offline transfer tool. The existing workstation still uses SQLite: PostgreSQL 18 accepts connections on 127.0.0.1:5432, but an authorized database login and local pgvector installation have not been verified. No PostgreSQL password was guessed, reset or disclosed. No destination database was overwritten. The tool does not change `.env` or select the application's active database.

## Transfer procedure

1. Provision a **new empty PostgreSQL database** with pgvector available, an authorized migration role, and a private `MIGRATION_DATABASE_URL` environment reference. Use the `postgresql+psycopg` driver. Do not put the URL on a command line or in chat. The migration role needs schema/extension creation privileges; a restricted runtime role should be provisioned separately afterward.
2. Preserve the original SQLite database, private `PROVIDER_SECRET_KEY`, artifacts, uploaded documents, repositories and local embedding cache. Database transfer does not copy external files or rewrite stored filesystem paths. Verify those files and permissions on the destination host separately. Backups inherit the private directory's Windows ACL; POSIX snapshots request mode 0600. These backups are not encrypted or offsite.
3. Run the dry run from the repository root: `.venv\Scripts\python.exe scripts/migrate_sqlite_postgres.py`. It creates and integrity-checks a retained SQLite snapshot, validates current schema, primary/foreign keys, audit chains and vault decryptability, then checks destination readiness/migration permissions in a transaction that is **rolled back**. Source must already be at the current Alembic head. Unknown tables, stale schema and occupied destinations are refused.
4. Stop every API/worker instance that writes the source. For the managed Windows installation use `scripts/stop.ps1`. Run `.venv\Scripts\python.exe scripts/migrate_sqlite_postgres.py --apply --confirm-services-stopped > data/migration-report.json`. The confirmation is an operator assertion, not proof that remote processes are stopped. During transfer the tool also holds a SQLite write lock to exclude racing writers.
5. All destination schema migrations and all inserts run in one serializable PostgreSQL transaction. Tables are transferred in foreign-key dependency order, with original keys, timestamps, integer monetary values, JSON, encrypted ciphertext and audit history. No constraints/triggers are disabled. Read back every table and compare row counts and canonical SHA-256 digests before commit. Vector hashes compare float32 values, the precision actually stored by pgvector. Audit chains and vault decryptability must pass again. A failure rolls back destination DDL/data and retains the source snapshot. An existing migrated-but-empty schema is supported; existing records are never merged, deleted or replaced.
6. Reverify using the backup path recorded privately in the report: `.venv\Scripts\python.exe scripts/migrate_sqlite_postgres.py --verify-backup data/backups/<snapshot>.db`. Keep services stopped during this comparison. After a network interruption around commit, use this verification to distinguish a completed transfer from rollback; do not blindly retry an occupied destination.
7. Explicitly configure **both API and worker** with the verified PostgreSQL `DATABASE_URL`, unchanged vault key/file roots, and `REQUIRED_DATABASE_BACKEND=postgresql`. Restart all instances so none retains an old SQLite engine/environment. The backend fence refuses startup when the configured backend differs. Compose pins the fence for migration/API/worker. Confirm owner login, `/health/ready`, Settings → Check database, scoped projects/approvals, saved conversations/workflows and semantic retrieval. Inspect worker heartbeat in the same database. Only then admit writes.

## Rollback and recovery

Before cutover/admitting PostgreSQL writes, the untouched SQLite source remains authoritative; restore the original explicit configuration and restart the managed services if destination verification fails. Once PostgreSQL accepts business writes, **do not switch back to the older SQLite snapshot**: that loses new records. Stop writers, preserve PostgreSQL and investigate/restore a separately verified PostgreSQL backup instead. Automated reverse replication, online dual writes and automatic cutover are intentionally absent.

The tool uses bounded lock/statement timeouts, an advisory transaction lock and table locks for empty existing destinations. CLI errors suppress driver URLs, SQL parameters and credential contents. A missing destination reference exits before snapshot or data changes. A successful JSON report must be stored privately; reports contain hashes/counts and a backup path, never record contents or credentials. Source/destination schema/data may still contain records too large or invalid for PostgreSQL; these cause rollback, not truncation.

The actual source snapshot passed checks with 52 tables and 14,257 rows at capture time. No live local PostgreSQL transfer/cutover is claimed.

The CI integration runs an actual SQLite → pgvector PostgreSQL transfer in an isolated temporary database, including large monetary balances, encrypted synthetic vault content, conversations/free-provider waits, semantic vectors and audit chains. It checks dry-run DDL rollback, failure after all rows are copied, successful read-back equality, occupied-destination refusal and wrong-key refusal. A separate drill stops writers, compares all table digests across a real database-container restart, performs `pg_dump`/`pg_restore` into a different database and compares again. TEST_REPORT.md records whether those checks passed for the published source. This is not a crash-kill, PITR, encrypted offsite backup or production restore certification.
