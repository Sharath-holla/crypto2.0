## Checkout boundary

The owner first imports an allowlisted GitHub repository with the existing metadata-only analyzer. POST /repositories/{id}/checkout saves an organization/project/import-bound request before contacting the trusted broker. No repository files or GitHub credentials enter the API/worker workspace. The broker reads the exact heads ref, commit tree and Git blobs through a GET-only credential capability. It refuses a moved branch, invalid ref/SHA, truncated discovery, links, submodules, traversal, case collisions, secret paths/content, unsupported binary content and size/time overruns. Every blob is checked against its Git object SHA; the receipt binds all file SHA-256 values and their aggregate digest to the original branch/commit/project.

This is a text source snapshot, not a Git clone/worktree. There is no .git directory, hook invocation, dependency installation, branch/commit creation, push or PR mutation. Binary assets and repositories containing forbidden secret-shaped paths, including .env.example, are deliberately refused rather than partially imported. Scoped connector verification against a real customer repository remains pending. Existing metadata-only repositories still cannot bypass the autonomous coding approval path.

Sources live only in the dedicated runner volume at /jobs/checkouts/<UUID>; API records contain provenance/receipts, never source files or tokens. Defaults are 500 files, 1 MB/file, 5 MB/snapshot, 90 seconds acquisition, eight retained snapshots and one-hour source TTL. Environment settings RUNNER_CHECKOUT_MAX_FILES, RUNNER_CHECKOUT_MAX_BYTES, RUNNER_CHECKOUT_TIMEOUT, RUNNER_CHECKOUT_MAX_RETAINED and RUNNER_CHECKOUT_TTL can tighten or adjust these within hard limits. A 30-second janitor, explicit cleanup, expiry-on-read and startup recovery remove source workspaces; interrupted acquisition is not silently repeated. Terminal broker receipts are retained for seven days. SQLite keeps the durable owner operation/audit record afterward.

Broker GITHUB_PUBLICATION_REPOSITORIES and AIVENTRA_GITHUB_TOKEN must be explicitly configured with scoped repository read access. The credential capability exposes Git object GETs only; no credential reaches a sandbox environment, model, database receipt or log. The broker's private RUNNER_TOKEN is a distinct API-to-runner capability. Generated containers never receive it or unrestricted Docker control. Compose's optional runner profile enables API and worker execution against the existing dedicated daemon; the local application remains disabled unless explicitly configured.

Acquisition never executes source. A separate ten-minute owner approval binds source digest, manifest, suite and timeout. Only the newest approval revision is valid, and one saved execution consumes it. Tests recheck project authority, current owner identity, source integrity and expiration. POST /repository-checkouts/{id}/execute uses the existing nonroot, network-disabled, capability-dropped, read-only-root, CPU/memory/PID/tmpfs-limited runner and its closed Python unittest/compile or Node test/syntax suites. A completed runner operation can have a failing exit code and is displayed as such. It does not imply independent product QA, acceptance or delivery success. Uncertain HTTP responses persist as interrupted; reconciliation reads the existing broker result instead of repeating execution.

Owner/scoped controls include bounded checkout listing, reconcile, cleanup, approve-execution, execute, saved execution listing/details and execution reconciliation. generic /records mutations cannot alter github_* operation records. The Engineering UI exposes these actions separately and can recover saved execution logs after a browser reload.

## PDF boundary

Requirements upload now accepts valid .pdf alongside existing text/DOCX formats. It checks filename, MIME, signature, strict PDF structure, EOF, encryption, active actions/JavaScript/embedded/XFA/RichMedia content and object counts. Text is extracted by fixed trusted parser code in a credential-free child process, never by executing a PDF or repository code. Windows Job Objects and POSIX resource limits cap RAM at 256 MB and CPU at three seconds; the parent kills parsing on its five-second wall timeout. Input is at most 1 MB, default page limit 50 (hard maximum 100), decoded stream 256 KB and extracted text 64 KB. Unsupported filters/structures are rejected. These limits can reject otherwise valid complex PDFs. The parser is a resource boundary around fixed code, not a general OS filesystem/network sandbox or a production security certification.

PDF_UPLOAD_LIMIT, PDF_PAGE_LIMIT and PDF_TIMEOUT_SECONDS are bounded configuration settings. Two concurrent parser slots cap process fan-out; excess uploads receive a retryable 429 without entering a database write transaction. No actions, links, embedded objects, external resources, images or OCR are executed/imported. Image-only documents return a specific no-usable-text error. pypdf is pinned through uv.lock; see its [reader API](https://pypdf.readthedocs.io/en/stable/modules/PdfReader.html) and [text extraction resource guidance](https://github.com/py-pdf/pypdf/blob/main/docs/user/extract-text.md).

Extracted text carries page markers, page count/text-presence metadata, original source SHA-256, extracted-content SHA-256, parser version, warnings, document version and replaced-source reference. Extracted/redacted Artifact content remains authoritative in SQLite. Original PDF bytes are retained in a private organization/hash-derived artifact location solely for owner reprocessing, with size/hash validation on reread. Raw files have no public download route. Removed/replaced versions remain private audit evidence; automated retention/garbage collection of original PDFs is deferred. Backups must include this private source directory in addition to SQLite and existing artifacts. Original DOCX binaries are still not retained.

Upload/replace/remove/reprocess require current draft version and UUID command identity. Reprocessing creates a new immutable artifact/version. Replaced/removed sources lose searchable chunks/grants and receive a permanent memory tombstone; subsequent synchronization cannot resurrect them. Unchanged copied brief text follows the new source; concurrent owner-written text is preserved. Submission freezes attachments. Later edits require the existing new requirement/proposal approval revision, not mutation of already-approved evidence. Exact proposal approval grants current source documents to the assigned project and existing permission-filtered memory.

## History boundary

GET /projects/{id}/history and /tasks/{id}/history return recent immutable audit events, default 20/max 50, with HMAC-signed organization/project/task-bound keyset cursors. New audit events store the existing locked Organization.version as _history_position inside their append-only hashed detail; no schema column or historical rewrite is needed. This prevents same-second random UUID ordering from admitting new events into older pages. Historical events keep position zero with stable timestamp/ID ties. Task history includes explicit task associations and events whose subject is that task. Full details retain existing source/approval/GitHub/delivery references without granting access to another tenant.

Conversation snapshots/SSE expose 20 recent turns; /conversations/{id}/history?before=<position> loads older immutable turn positions. Page attachments are bounded to the page's referenced IDs and 20 recent uploads; loading older UI pages merges these IDs. Existing workflow, routing explanation, trace, consultation and document references remain. Conversation-list cursors bind the saved updated_at/ID and search/organization rather than rereading a mutable cursor record. The UI deduplicates IDs, rejects stale search responses and retains older loaded turns during new SSE activity. A reload starts with the bounded recent page again.

/state retains current registries/project/task/reference data while historical messages/audits/runs/traces/events/notifications default to 30 rows each; an explicit history_limit accepts 1–300. It uses stable timestamp/ID ordering. This bounds initial serialization without deleting any records. Project Timeline and task details/QA display actual saved events with Refresh/Load older controls.
