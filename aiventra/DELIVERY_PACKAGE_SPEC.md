# Immutable delivery packages

The Phase 5 continuation is preserved in docs/PHASE5_COMPLETION_SPEC.md. Package preparation extends the existing final review and durable Workflow/WorkflowStep worker. SQLite remains active. Additive migration c72e51d9af04 introduces delivery_packages with tenant/project version and request uniqueness, foreign keys and database guards preventing finalized content mutation or version deletion on SQLite/PostgreSQL.

An owner selects a completed final review and exact source hash, supplies release notes/summary/limitations and explicitly maps reviewed documents to architecture decisions, HLD, LLD, database, API and deployment instructions. These mappings are owner selections, not automatic semantic certification. Every document must already belong to the reviewed task source. Missing purposes are persisted as explicit package blockers. Client disclosure is opt-in for mapped documents.

Preparation validates all five role artifacts, successful model results, participant identity and exact workflow checkpoints, and rechecks current source/approval/budget evidence. Fixture inference provenance cannot authorize a live package. The worker saves validation then freeze checkpoints; pause/resume/cancel use existing leases and controls. Duplicate request IDs return the original version; competing preparations serialize through the organization lock. New content creates a new version and a supersedes reference.

Manifest hashing uses canonical JSON/SHA-256. Private UTF-8 files are stored under generated organization/hash paths inside the existing artifact root. Atomic no-replace publication preserves full files across interrupted writes; each read verifies byte length and SHA-256. Linked paths, traversal, oversize, binary and detected sensitive content fail closed. Files are capped at 500 KB each/2 MB total, not arbitrary SQLite binary blobs. Deployment stays unverified without a real connector. Existing runner source patches and compilation/test receipts can be included; these are not exported deployable binaries or a verified staging site.

Owner-only package inspection/download uses actual integrity checks and no-store attachment responses through the authenticated Next proxy. A fixture package is visibly fixture_nonproduction even when package_ready; it cannot constitute client release. Separate release approval, invitation/project grants, client responses and closure are now implemented in the following domain modules described in CLIENT_DELIVERY_WORKFLOW.md and ARCHITECTURE.md. No generated PR, paid inference or real delivery is authorized by package preparation.
