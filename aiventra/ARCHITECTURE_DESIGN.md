# Versioned architecture decisions

Phase 7 extends the existing CTO consultation, proposal selection, staffing planner and restricted engineering workflow. It adds no database or parallel workflow engine. Older proposals retain their original approval contract.

After exact requirements sign-off, the CTO returns a bounded `TechnicalDesign`: up to five uniquely named options, a recommendation, HLD, LLD, API and database specifications, authentication/data flow, topology, observability, verification, resource/cost assumptions, security impacts and ADRs. One option requires an explicit explanation. Benchmarks and cloud prices remain unverified. These are proposed designs, never execution receipts.

Each option is saved as a hashed artifact. The existing project draft stores a manifest bound to requirements ID/version/scope hash, successful CTO ModelRun, workflow/checkpoint and complete canonical design. Earlier manifests/documents remain in version history. Every publication, selection and project-authority check validates scope authority, artifact bytes, option/document correspondence, successful run, agent/checkpoint identity and mode. Deterministic test adapters are labeled `FIXTURE_TESTED`; successful real execution would be `MODEL_EXECUTED`, not independent certification.

The Lead synthesizes a proposal using the saved options. Backend publication canonicalizes alternatives from CTO evidence and recalculates deterministic incomplete cost estimates. The owner reviews the design and selects an option through the existing proposal approval control. One serialized transaction saves separate `architecture_design` and `proposal` approvals, creates the project and suggested workforce, and attaches the selected design to scoped persistent memory. Architecture approval binds manifest/scope/selection/version, has an enabled owner and 30-day expiry, and does not authorize staffing execution, repository changes, publication or deployment. Same-selection retries return the existing project without duplicate approvals; another selection conflicts.

Request-changes/reject stores the reason under the same organization lock as approval. A competing decision has one winner. Before project creation, an owner can save a fresh requirements revision and sign-off, then obtain a new CTO design; historical documents and decisions remain. Approved project changes keep the existing versioned change controls. Planning and coding prompts receive the actual owner-selected design rather than silently using the recommendation; their existing authority gates validate the separate architecture approval.

The no-model manual path saves one `OWNER_AUTHORED_LIMITED_PLAN` document with explicit limitations. It claims no CTO execution, complete HLD/LLD or independent analysis. It still requires exact requirements and architecture selection approvals. An unavailable model persists its waiting state; there is no fixture fallback in live execution.

The current proposal screen and project Requirements section render saved design details, evidence basis and document hashes. Existing five-stage navigation is retained. Document-task handoffs also carry the exact owner-selected design explicitly, alongside planning, coding and review context. The existing harmless Task API engineering journey has retained legacy and Phase 7 variants, including a non-recommended selection, exact workforce/repository gates, failed build, one bounded repair, independent review and unpublished candidate. Local runner/model adapters remain explicit fixtures; CI replaces only the runner with actual restricted Docker and retains the prohibition on fixture release/publication.

Three-stage QA, deterministic release quality/traceability and restricted DevOps target/deployment reconciliation are subsequent Phase 7 work; an architecture approval is not proof of a complete delivery lifecycle.
